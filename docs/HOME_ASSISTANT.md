# Smart Home: IR remote and Home Assistant (Home tile 5, screens SH10-SH12)

One tile, two integrations. The **IR remote** drives the Cardputer's own IR LED and needs no backend. **Home
Assistant** (lights, switches, locks, ...) goes through the PC backend and an owner-written allowlist. Code:
`firmware/src/modules/{smart_home,ir_remote}.cpp`, `firmware/include/ir_remote.h`,
`firmware/lib/oyster_core/{include/oyster_core/ir_codes.h,src/ir_codes.cpp,include/oyster_core/home_json.h,src/home_json.cpp}`
(device); `backend/oyster/home/` (backend). Tests: `firmware/test/test_smarthome/`, `tests/home/`. Example
allowlist: `examples/home_allowlist.example.json`.

## Status, stated plainly

- **IR codes: unverified.** The code tables come from public protocol documentation and open TV code lists and
  are checked in the host tests against the MSB-first hex codes those lists print. **No code has been tried on
  a real TV.**
- **IR LED pin: unverified.** GPIO44 is the pin of the M5Stack Cardputer example; it has not been confirmed on
  this Cardputer ADV unit. If nothing reacts, this is the first suspect (look at the LED with a phone camera).
- **Home Assistant: unverified against a real instance.** The owner has no URL or token yet. The backend is
  tested against a fake Home Assistant (`httpx.MockTransport`); the firmware has not run on a Cardputer. Until
  `HOME_ASSISTANT_URL`, `HOME_ASSISTANT_TOKEN` and an allowlist file exist, the tile shows
  "Home Assistant: not set up" and explains what is missing; the IR part works without any of it.
- **IR cannot know whether the TV obeyed.** The screens say "Sent", never "done". There is no learn mode (no IR
  receiver) and no air-conditioner code (no well-known code could be sourced).

## Screens

| Screen | Content | Keys |
| --- | --- | --- |
| SH10 rooms | `IR Remote (5 TVs)`, then the Home Assistant rooms, or one muted status row: `not set up`, `loading`, `offline`, `no backend` | Enter opens; a muted row opens a text that explains it; `r` refreshes |
| SH11 devices (IR) | `TV Samsung`, `TV LG`, `TV Sony`, `TV NEC (Toshiba type)`, `TV Philips (RC5)`, `About IR codes` | Enter opens |
| SH12 keys (IR) | `1 Power`, `2 Vol+`, `3 Vol-`, `4 Mute`, `5 Ch+`, `6 Ch-` | Enter sends the row, `1`-`6` send that key; the strip shows `sending` for the ~100 ms of the frame; a toast says `Sent: Power (IR, no reply)` |
| SH11 devices (HA) | `label` and the state Home Assistant reported; `!` after the label = impactful | Enter opens, `r` refreshes |
| SH12 actions (HA) | the actions the allowlist lists for the entity (`Turn on`, `Lock`/`Unlock`, `Open`/`Close`, ...) | Enter or `1`-`3` sends; impactful entities open a Confirm page first |

- **Confirm page** (locks, covers, alarm panels, anything marked `impactful`): operation, target and effect are
  shown; Enter sends, Back or Cancel rejects and nothing is sent. The framework ignores keys for the first 700
  ms. The request carries `confirmed: true` only after that Enter.
- After an action the toast shows `label: state` as Home Assistant reported it, or `Not done: <reason>`. A
  lost connection says `No answer; result unknown. Check it` because the action may have run.
- One Home Assistant action is in flight at a time (`Wait for the last answer`); an answer that never comes is
  given up on after 20 s and a late request then does nothing.
- Home tile status line: `IR+HA` (Home Assistant answered), `IR only` (not set up or not asked yet), `offline`
  (the last Home Assistant request failed).

## IR remote

The IRremote library (4.7.1, already pinned) sends; this is the only file that includes it
(`ir_remote.cpp`). The carrier is generated by the LEDC peripheral (channel 0; the display backlight uses
channel 7), no receive code is compiled in and no timer interrupt is installed. The pin is attached for one
frame and then parked low and detached, so nothing keeps running. A frame is sent on the **worker task**
(`modules::request`), never on the UI task, and blocks it for the frame: about 70 ms (NEC, Samsung32, RC5) or
about 140 ms (SIRC sends 3 frames). Because module calls hold the radio lease, a send is refused with
`Radio busy; try again` while a Wi-Fi or BLE operation runs.

| Brand row | Protocol | Address | Power | Vol+ | Vol- | Mute | Ch+ | Ch- | Family |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| TV Samsung | Samsung32 | 0x07 | 0x02 | 0x07 | 0x0B | 0x0F | 0x12 | 0x10 | MSB-first lists print `E0E0xxxx` |
| TV LG | NEC | 0x04 | 0x08 | 0x02 | 0x03 | 0x09 | 0x00 | 0x01 | `20DFxxxx` |
| TV Sony | SIRC 12 bit, 3 frames | 1 | 21 | 18 | 19 | 20 | 16 | 17 | `A90`, `490`, `C90`, `290`, `090`, `890` |
| TV NEC (Toshiba type) | NEC | 0x40 | 0x12 | 0x1A | 0x1E | 0x10 | 0x1B | 0x1F | `02FDxxxx`; a code family shared by many relabelled sets |
| TV Philips (RC5) | RC5 | 0 | 12 | 16 | 17 | 13 | 32 | 33 | system 0 = TV |

Values are in the IRremote convention (what the library prints when it decodes the remote), not the MSB-first
hex that some lists print: `ir_codes.h` documents it and `test_smarthome` converts every NEC, Samsung32 and
SIRC entry to the printed form and compares. A Toshiba-type or other set that does not react may use another
code family: add a row to `kBrands` in `ir_codes.cpp` and a test.

## Home Assistant: backend setup

Environment (`backend/.env`; read once at start-up, so restart the backend after changing them). Values are
never logged, never returned by any route and never shown on the device.

| Variable | Meaning |
| --- | --- |
| `HOME_ASSISTANT_URL` | base URL, `http://<host>:8123` or `https://...`; no credentials, query or fragment in it |
| `HOME_ASSISTANT_TOKEN` | long-lived access token (Home Assistant: profile page > Security > Long-lived access tokens) |
| `HOME_ASSISTANT_CA` | optional: PEM file to trust for an `https` URL with a private CA |
| `OYSTER_HOME_ALLOWLIST` | path of the allowlist JSON; default `home_allowlist.json` in the data directory (a relative path is relative to the data directory) |

- TLS verification is always on for `https`. A plain `http` URL works (the usual Home Assistant default) but the
  token then crosses the LAN unencrypted: the backend logs a warning at start-up and `GET /v1/home/status`
  shows `"tls": false`.
- Redirects are never followed, timeouts are 5 s, the system proxy settings are ignored, answers larger than
  64 KiB are refused, and the HTTP library's own request log lines (which print the URL) are suppressed.
- The allowlist file is re-read when it changes; an invalid file switches Smart Home off (nothing is
  allowed) and `GET /v1/home/status` lists the problems.

### Allowlist

```json
{"version": 1, "rooms": [{"id": "living", "name": "Living room", "entities": [
  {"entity_id": "light.living_ceiling", "label": "Ceiling light", "actions": ["turn_on", "turn_off", "toggle"]},
  {"entity_id": "lock.front_door", "label": "Front door", "actions": ["turn_on", "turn_off"]}]}]}
```

Anything not in the file cannot be read or controlled. Limits: 16 rooms of 16 entities; room `id` is
`a-z 0-9 _ -` (1-24); `name` and `label` are printable ASCII (1-24, the device font); each entity appears once;
unknown keys are errors. Any violation makes the whole file invalid (a typo never silently changes access).

| Domain | `turn_on` | `turn_off` | `toggle` | Impactful |
| --- | --- | --- | --- | --- |
| `light`, `switch`, `fan`, `input_boolean`, `humidifier`, `media_player`, `climate` | `turn_on` | `turn_off` | `toggle` | only if marked |
| `scene` | `turn_on` (activate) | - | - | only if marked |
| `lock` | `lock` | `unlock` | - | always |
| `cover` | `open_cover` | `close_cover` | `toggle` | always |
| `alarm_control_panel` | `alarm_arm_away` | - | - | always |

Other domains (scripts, automations, shell commands, ...) are refused when the file is loaded. An alarm panel
can be armed but not disarmed from the device: disarming needs a code, which this code never stores. A
`"impactful": true` flag adds the local confirmation to any entity; the always-impactful domains cannot be
unmarked.

## Backend API

Wiring: `install_home(app)` in `oyster.main.create_app`, right after `install_deck`. The device routes are served
on both listeners; the owner routes only on the loopback listener (ADR-004), and the owner token is refused on
the device listener as everywhere else. One runtime per data directory is shared by both listeners.

| Route | Who | Answer |
| --- | --- | --- |
| `GET /v1/home/rooms?limit=&after=` | device, owner (loopback) | `{"configured": bool, "reason"?, "rooms": [{"id","name","count"}], "next_after"}` (<= 16 per page). Unconfigured: `configured:false`, a `reason` (`no_url`, `bad_url`, `no_token`, `bad_token`, `no_allowlist`, `bad_allowlist`, `no_rooms`) and no rooms; Home Assistant is not contacted. Configured: one reachability check (`GET /api/`, remembered 10 s) so `configured:true` means it answered with the token |
| `GET /v1/home/rooms/{room_id}/devices?limit=&after=` | device, owner (loopback) | `{"room": {"id","name"}, "devices": [{"entity_id","label","state","impactful","actions"}], "next_after"}` (<= 8 per page). States are read one by one inside an 8 s budget: `missing` (Home Assistant does not know the entity), `unknown` (out of time), `scene` (scenes are not read) |
| `POST /v1/home/actions` | **device token only** | body `{"entity_id","action","confirmed"?}`, header `Idempotency-Key` (8-80 chars `A-Za-z0-9._:-`); answer `{"entity_id","action","result":"ok","state","duplicate"}` |
| `GET /v1/home/status` | owner (loopback) | what is set (`url_set`, `token_set`, `tls`, `ca_file_set`), allowlist counts and problems; never the URL or the token |
| `GET /v1/home/audit?limit=&before=&device_id=` | owner (loopback) | newest first, <= 50 per page |

An action request is checked in this order, and nothing after a failing step runs: per-device rate limit (20
actions and 60 reads per minute) > configuration complete > entity in the allowlist > action in the entity's
list > impactful entity needs `confirmed: true` > idempotency > audit row "pending" > Home Assistant call >
audit row with the outcome. The owner token cannot post actions: the confirmation is a key press on the
Cardputer and only an authenticated device can send it.

| Status / code | Meaning |
| --- | --- |
| 401 / 403 | missing or invalid token / wrong role (the owner token on an action, a device token on an owner route) |
| 404 `not_found` | room or entity not in the allowlist (also for malformed room ids) |
| 403 `action_not_allowed` | the entity does not list that action |
| 409 `confirmation_required` | impactful entity without `confirmed: true`; nothing was sent |
| 409 `idempotency_conflict` / `request_in_progress` | the key belongs to another request / the same request is still running |
| 422 `validation_failed`, 413 `payload_too_large` | malformed body or key (bodies <= 4 KiB) |
| 429 `rate_limited` | with `Retry-After` |
| 503 `home_not_configured` | URL, token or allowlist missing or invalid |
| 503 `home_unreachable`, `home_timeout` | cannot connect / no answer in 5 s (`home_timeout` on an action: the outcome is unknown) |
| 502 `home_auth_failed`, `home_refused`, `home_upstream_error` | the token was refused / Home Assistant rejected the call / unexpected answer |
| 503 `audit_unavailable` | the audit file cannot be written; nothing was done |

Idempotency: the key is scoped to the device and stored as a hash with the answer of an **executed** action
for 24 h (at most 1000), in `home.db`. The same key with the same request returns the stored answer with
`"duplicate": true` and does not touch Home Assistant, also after a restart; the same key with another request
is a 409. A failed action does not use up its key. The device sends one fresh key per key press and does not
retry by itself.

Audit (`home.db`, append-only at the database level): who (device id), room, entity id, generic action,
whether `confirmed` was sent, outcome (`pending`, `ok`, `failed`, `unknown_outcome`, `replayed`, `denied`),
a reason code and the hash of the idempotency key. Denied attempts are recorded; successful reads and
malformed requests are not. No token, URL, plain key or request body is ever stored. `home.db` is created on
first use.

## Device parsers

`home_json.h` parses the three answers and the error body with ArduinoJson under hard bounds: input <= 5120
bytes, nesting <= 6, ArduinoJson filters keep only the used keys, every string is cut to its buffer and reduced
to printable ASCII, entity and room ids must match the allowlist grammar, rooms and devices beyond 16 are
dropped, wrong types are treated as absent. `test_smarthome` feeds hostile fields, every prefix of valid
documents and flipped bytes.

## Verification checklist (needs the device and the real services)

1. **IR LED pin.** Open Smart Home > IR Remote > a brand > Power with the Cardputer ADV pointing at a phone
   camera: the LED should flicker while the strip says `sending`. No light: GPIO44 is wrong for this unit
   (change `ir::kTxPin` in `ir_remote.h`).
2. **Each TV.** Try Power, Vol+/Vol-, Mute, Ch+/Ch- on the brand that matches the TV; record which rows work
   (record failures too: a family that does not react needs its own code row).
3. **Not set up.** With no `HOME_ASSISTANT_*` in `backend/.env`: tile status `IR only`, the room list shows the
   muted row, Enter explains the missing names, IR still works.
4. **Real Home Assistant.** Set URL, token and an allowlist (start from `examples/home_allowlist.example.json`,
   real entity ids), restart the backend: tile status `IR+HA`, rooms and states match Home Assistant, a light
   toggle changes the light and the toast shows the state Home Assistant reports.
5. **Impactful.** A lock or cover action opens the Confirm page, Back sends nothing, Enter acts; check
   `GET /v1/home/audit` shows `confirmed: true` for it.
6. **Failure paths.** Stop Home Assistant: rooms show `offline`; wrong token: `rejected the token`; backend
   off: `No answer from the PC backend`. None of them blocks the IR keys.

## Not done

- No learn mode and no AC codes (no IR receiver; no sourced code). No IR repeat while a key is held.
- No MQTT, no scripts or automations, no disarming of alarm panels, no per-device allowlists (the file applies
  to every enrolled device), no Home Assistant event subscription (states are read when a room is opened or
  refreshed).
- The IR frame timing is a busy wait on the worker task: heavy Wi-Fi traffic during the ~100 ms could distort it
  (unverified).
